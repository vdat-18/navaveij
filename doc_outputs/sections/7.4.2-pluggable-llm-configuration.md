# 7.4.2 Pluggable LLM Configuration Management

The AI gateway is designed to be fully provider-agnostic. The active model is a **configuration value**, not a code dependency. Switching from one model to another — whether across providers, model sizes, or deployment modes — requires a single configuration update and a service restart. No application code changes, no redeployment, and no schema migration are needed.

### Zero Vendor Lock-In

This architecture was a deliberate design choice to protect the project against the rapid pace of change in the AI model landscape. As newer, more capable models become available from different providers, the hospital is free to adopt them immediately. Similarly, if cost, data sovereignty, or regulatory requirements shift — such as a need to move from cloud inference to fully on-premise — the transition can be made at the configuration layer without touching any clinical logic.

### Supported Provider Categories

| Provider Category | Example Models | Deployment Mode |
|---|---|---|
| Cloud AI labs | GPT-4o (OpenAI), Claude 3.5 Sonnet (Anthropic), Gemini (Google), and equivalents | Cloud |
| Open-source self-hosted | Llama 3.x, Mistral, Qwen, and compatible open-weight models | On-premise or air-gapped |
| Model aggregator | Routing-based access to a broad catalogue of models from multiple providers | Cloud |

### Configuration Model

The active model is selected by setting a single environment variable at deployment time. The fallback chain — the ordered list of candidates the gateway will try if the primary model fails — is also declared in configuration, not in code.

This means the same application build can serve different model configurations across environments: a lightweight open-source model for development and testing, a proprietary cloud model for production, or a fully air-gapped on-premise model for a data-sovereign deployment — all without branching the codebase.
