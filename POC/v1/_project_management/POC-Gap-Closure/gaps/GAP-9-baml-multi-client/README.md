# GAP-9 — BAML Multi-Client Configuration (Pluggable AI)

**Severity:** 🟡 Low
**Execution order:** Step 9 — independent; can be done any time after GAP-1
**Estimated effort:** 30–45 minutes
**Category:** AI Config

---

## Why This Matters

`baml_src/clients.baml` has a single `NavaveijClient` hardwired to Google AI. The `.env.example` is set up for a local OpenAI-compatible LLM (`LLM_BASE_URL=http://127.0.0.1:1234/v1/`) — but the BAML client reads `GOOGLE_API_KEY` instead of `LLM_API_KEY`. The POC currently only works because a `.env` file (not committed) has the correct Google key hardcoded.

The spec requires model switching through a config file or setup screen without modifying source code:
> "Swapping models requires only an admin panel update — no code change, no redeployment."

**Current mismatch:**
- `clients.baml` → `provider google-ai` → reads `GOOGLE_API_KEY`
- `.env.example` → `LLM_BASE_URL=http://127.0.0.1:1234/v1/` (OpenAI-compatible)

The Phase 6 demo includes a model switcher dropdown. This gap makes it impossible to demonstrate switching between Claude and GPT-4o without editing BAML source.

**POC evaluation impact:** 25% Data Standards / Architectural Flexibility criterion

## Step-by-Step Instructions

### 9a — Update `baml_src/clients.baml`

Replace the current single-client definition with three named clients plus a config-driven alias:

```baml
// Google AI (Gemini)
client<llm> NavaveijGoogleClient {
  provider google-ai
  options {
    api_key env.GOOGLE_API_KEY
    model env.LLM_MODEL
  }
}

// OpenAI-compatible (local LLM via LM Studio, or OpenAI, or Azure OpenAI)
client<llm> NavaveijOpenAIClient {
  provider openai
  options {
    api_key env.LLM_API_KEY
    base_url env.LLM_BASE_URL
    model env.LLM_MODEL
  }
}

// Anthropic Claude
client<llm> NavaveijAnthropicClient {
  provider anthropic
  options {
    api_key env.ANTHROPIC_API_KEY
    model env.LLM_MODEL
  }
}

// Active client — change LLM_CLIENT_ALIAS to switch providers without any code change
// Valid values: NavaveijGoogleClient | NavaveijOpenAIClient | NavaveijAnthropicClient
client<llm> NavaveijClient = env.LLM_CLIENT_ALIAS ?? NavaveijOpenAIClient
```

> The `??` fallback means if `LLM_CLIENT_ALIAS` is not set, it defaults to `NavaveijOpenAIClient` (matching the existing `.env.example` setup).

### 9b — Update `POC/.env.example`

Add the new variables:

```
# ── Pluggable AI provider ────────────────────────────────────────────────────
# Switch providers without any code change — update LLM_CLIENT_ALIAS and restart
# Valid values: NavaveijGoogleClient | NavaveijOpenAIClient | NavaveijAnthropicClient
LLM_CLIENT_ALIAS=NavaveijOpenAIClient

# Google Gemini (used with NavaveijGoogleClient)
GOOGLE_API_KEY=        # Get from Google AI Studio

# Anthropic Claude (used with NavaveijAnthropicClient)
ANTHROPIC_API_KEY=     # Get from Anthropic console
```

### 9c — Regenerate `baml_client/`

```bash
cd /path/to/repo/root   # where baml_src/ lives
baml-cli generate
```

This regenerates the Python client in `baml_client/`. The existing BAML function calls in `clinical.py` and `validator.py` (`b.GenerateRecommendation`, `b.ValidateRecommendation`) do not need to change — they all route through `NavaveijClient`.

## Verification

**Test Google provider:**
1. Set `LLM_CLIENT_ALIAS=NavaveijGoogleClient` and `GOOGLE_API_KEY=<your_key>` in `.env`
2. Restart server, run `POST /api/recommend {"patient_token": "tok_hmac_56291047"}`
3. Check `POC/logs/audit.jsonl` last entry: `what.model_id` should contain `"gemini"`

**Test local OpenAI-compatible provider:**
1. Start a local LLM server (e.g. LM Studio at `http://127.0.0.1:1234/v1/`)
2. Set `LLM_CLIENT_ALIAS=NavaveijOpenAIClient`, `LLM_API_KEY=`, `LLM_BASE_URL=http://127.0.0.1:1234/v1/`, `LLM_MODEL=<your-local-model>`
3. Restart server, run recommendation
4. Check `what.model_id` in audit log shows the local model name

**Model switch demo (for Phase 6):**
- Changing only `.env` (no code change, no redeployment) switches the active AI provider
- The audit log records which model was used in every entry — change is immediately verifiable
